FitIQ

Live v1.5.5 · Solo project

Problem

My household wanted one place to plan workouts, log sets on a phone mid-workout, and track progress, with each person's data private and no hosting bill.

My role

Solo: design, build, tests and deployment.

What I built

  • An installable PWA in React and TypeScript on GitHub Pages. The browser talks straight to Supabase Auth and Postgres; there's no custom backend.
  • Privacy enforced in the database: Row Level Security on every table, plus ownership triggers so no row can point at another person's data.
  • An 876-exercise library, reusable plans, and one-handed set logging that saves each set the moment it's completed, so a sleeping phone loses nothing.
  • History, personal records, weight and measurement charts, and a public demo account that reseeds every week.

Stack

React, TypeScript, Vite, Supabase (Auth + PostgreSQL), Playwright, GitHub Actions, GitHub Pages

How it's verified

A two-account RLS test checks every table, including cross-parent cases (188 checks). Playwright end-to-end tests of the main flows run in GitHub Actions against a local Supabase stack.

Limitation

With no backend of my own, any rule beyond "this row is yours" has to live in Postgres policies and triggers. It runs within the free tiers of my current deployment, which caps how far it can grow.

PalletIQ

Active development Floor app v1.11.1 · API v1.4.0 · Manager app v1.0.0 · Solo project

Problem

Warehouse software is often built for a desk, not for someone with a scanner on the floor. PalletIQ is an independent inventory system designed around how the floor works, informed by ~9 years in inventory control at a Target distribution center. It uses synthetic data only.

My role

Solo: design, data model, all three apps, and tests.

What I built

  • Floor app (React, tablet): badge + PIN login, directed and manual Pull and Put driven by label scans, Pallet ID and Location ID screens reachable from any reference, an Empty Locations aisle summary and zone map, and productivity reports.
  • Manager app (Electron): password login, Audit Tool, Location Setup, Job/Function Assignment, Prod Goal / Daily Plan, Team Prod Summary, and the floor app embedded in a window.
  • Shared API (Express + Prisma on MySQL): signed JWTs, reservation locking so two people can't claim the same location, and a four-tier role hierarchy with field-level permissions.
  • Shared TypeScript package for types and pure domain rules, so a data-shape change is a compile error in every app.

Stack

React, TypeScript, React Router, Vite, Tailwind CSS, Electron, Node.js, Express, Prisma, MySQL, Playwright

How it's verified

A written test plan backed by unit, database and handler suites for the API, Vitest + Testing Library tests for both apps, and Playwright end-to-end suites (the desktop tests drive the built Electron app), all run against an isolated Docker MySQL test database.

Limitation

It runs locally on my Mac and isn't hosted yet, so there's no live demo; moving it to my home server (Voyager) is planned. Two manager screens, DPCI Setup and Hung Pallet Resolution, aren't built yet. It started on Azure SQL; I moved it to MySQL.

ScribeIQ

Stable v1.0.2 · macOS on Apple Silicon · Solo project

Problem

I wanted call transcripts that show who said what, without sending the audio to a cloud service.

My role

Solo: architecture, Python back end, React UI, and integrating the Swift recorder helper.

What I built, and the decisions behind it

  • Two tracks, not one mix. A small Swift helper on Apple's ScreenCaptureKit records the mic and one chosen app's audio on a shared clock. My lines are labeled by which track they came from, so speaker detection only runs on the other side of group calls.
  • The server owns the recording state. FastAPI runs the state machine and supervises the helper over stdin/stdout. The UI's buttons follow the server, and if the app crashes the helper sees its input close, saves and exits.
  • Local inference. MLX Whisper transcribes each track on the Mac after recording; pyannote splits the other side into speakers, and a speaker can be renamed everywhere with one click.
  • Local-only server. It listens on 127.0.0.1 and checks the Host and Origin headers, so another web page can't start or stop a recording.

Stack

Python, FastAPI, WebSockets, React, TypeScript, Vite, Vitest, MLX Whisper, pyannote.audio, pywebview; integrates a Swift + ScreenCaptureKit helper

How it's verified

Python tests cover track merging, the recording state machine, the recorder protocol and every API endpoint, using a fake recorder and stubbed transcription. The UI has Vitest + Testing Library tests, and a Playwright suite runs the app end to end.

Limitation

macOS 15+ on Apple Silicon only, so most visitors can't install it. Transcription runs after the call, not live, and labels on the other side can slip when people talk over each other. Recording laws vary; let people know before you record.

Family Passport Map

Live v2.5.0 · Solo project

Problem

My family wanted to see who has been to which states and countries, on a phone or a laptop, without anyone else seeing their photos or travel.

My role

Solo: design, build, tests and deployment.

What I built

  • Interactive US and world maps (195 countries, one continent at a time); click a place to mark it visited for the selected person.
  • A color and profile picture per person, "n/50 states" and "n/195 countries" counters, a side-by-side Compare view, and a List view.
  • Sign in with Microsoft, Google, GitHub or a passkey, and add or remove methods on a Sign-in methods page. Each account sees only the People it owns (up to 10), and photos are shrunk to small avatars served only to their owner.
  • A guest demo on GitHub Pages: the same app running in the browser against an in-browser fake API, with a made-up family.
  • Installable as a PWA on phone, tablet and desktop.
  • Hosted in Docker on my home server, Voyager, since v2.5.0 (moved from Azure App Service).

Stack

React, TypeScript, Vite, Tailwind CSS, Node.js, Express, Prisma, SQLite, WebAuthn (passkeys), Playwright, Docker, Cloudflare Tunnel, GitHub Pages

How it's verified

Server tests for every sign-in method (passkeys checked with a software authenticator), ownership checks, private photos, visits and account deletion. Playwright covers every user flow at desktop and phone sizes, and API contract tests run the same scenarios against the real server and the demo's fake API so the two can't drift apart.

Limitation

It runs on a home server, so it goes down if the power or home internet does. Sharing People between accounts (Link and Join) is next.

No account needed for the guest demo: it runs in your browser with a made-up family, and reloading starts over.

LensIQ

Live v1.1.0 · Self-hosted on Voyager

Self-hosted dashboards for Notion: tables, boards, charts and calendars over Notion databases, edited in place and written straight back to Notion.

Notion's free plan allows one chart. LensIQ keeps Notion as the data store and adds the views a paid plan would. It reads each database's schema and builds every view from it, so connecting a new database means pasting its link, not writing code. It runs as one Docker container on Voyager behind Cloudflare Access, and the Notion token never leaves the server.

Highlights

  • Table, board, chart and calendar views per database, each with its own filters and sorts
  • Dashboards mixing views from any databases, in a grid that stacks to one column on a phone
  • Edits go straight to Notion; the API re-reads the page first, so a cell changed in Notion meanwhile is never silently overwritten
  • Rows cached in SQLite and refreshed every 60 seconds, with every Notion request going through one rate limiter
  • A public demo: the same React app answering its API calls in the browser from fictional data

How it's verified

Vitest + Testing Library unit tests, and Playwright end-to-end tests at desktop and phone sizes against a fixture Notion server.

Stack

React, TypeScript, Vite, Tailwind CSS, TanStack Query, Recharts, Node.js, Fastify, SQLite, Notion API, Docker, Cloudflare Access + Tunnel, Vitest, Playwright

TLDR Reader

Live v2.1.0 · New items each weekday

A personal reader for the TLDR newsletter: browse by day and edition, flag items to a reading list, and save favorites.

A deterministic Node.js pipeline, run each weekday morning by GitHub Actions, collects the day's items from all 14 TLDR editions and publishes them as static JSON. Reading-list and saved-item state lives in Azure Cosmos DB behind Microsoft sign-in.

Content boundary: it stores each item's headline and TLDR's short summary, with a link to the original article. I built it for my own reading; it isn't affiliated with TLDR.

Highlights

  • Browse This Week and Last Week by day and newsletter edition
  • Archive calendar: pick any past date with items
  • Flag items to a Reading List; star them to save
  • Microsoft (Azure AD) sign-in with per-user state
  • Planned: edition and date filters and keyword search for saved items

Stack

Voicewright

Stable v1.0.0 · Runs locally on a Mac

A local text-to-speech app: design a custom voice from a description, then render a tagged script to one audio file.

Designs AI voices from a text description, then turns a tagged script into a finished audio file that mixes emotions and sound effects, for example [calm] The library opens at nine. {page turn}. The models run on the Mac; the only network use is searching Freesound to fill the local sound library. A FastAPI back end runs model jobs in the background and serves a local web page.

Highlights

  • Voice design with Qwen3-TTS VoiceDesign: a neutral clip plus one preset per emotion
  • Speech and voice cloning with Chatterbox on MLX
  • Review voices take by take: regenerate, retune, or roll back to an earlier take
  • Sound library from Freesound, stored with each sound's credit and license
  • Script editor with tag highlighting and a check that reports every problem at once

How it's verified

The v1 QA pass checked all 61 user stories against the running app. Most were checked by a script that drove the page in headless Chrome with the real models; window launch, install, keyboard behavior and drag and drop were checked by hand. There are also 400 unit tests, 66 Playwright browser tests that drive every area of the page on fake models, and an offline smoke test with the real models.

Stack

Python, FastAPI, JavaScript, HTML, CSS, Qwen3-TTS, Chatterbox (MLX), pytest

Voyager

Live Home server · Hosting 2 apps, more moving in

A 2011 MacBook Pro rebuilt as an always-on, headless Ubuntu server that hosts my apps in Docker behind a Cloudflare Tunnel.

I wiped macOS, installed Ubuntu Server 26.04 LTS, and run the machine headless with the lid closed. Every app is one folder with one Compose file and its own secrets, so projects stay easy to move when the server is replaced. It's a stopgap until I buy better hardware: 2 cores, 16 GB of RAM and a spinning hard drive are plenty for portfolio traffic, not for heavy work.

Running on it now

  • Family Passport Map: moved from Azure App Service in v2.5.0, live at passport.bobbyjoecool.dev
  • LensIQ: my Notion dashboards, behind Cloudflare Access so only listed accounts get in
  • A Cloudflare Tunnel (cloudflared) that publishes both sites with no open router ports
  • A Samba file share for the house
  • A nightly backup job (cron) that archives app data and keeps 14 days of copies

Planned moves

  • PalletIQ: the floor app, API and MySQL database, giving it its first live site
  • Moffat Bay Marina: off Azure App Service and Azure Database for MySQL, so it no longer sleeps between visits
  • The Work Job Tracker database, if I start using it from more than one computer

How it's set up

  • Images built for amd64 on my ARM laptop with Docker buildx, then loaded over SSH
  • Only web-facing containers join the tunnel's network; databases stay private and bind to localhost only
  • Tailscale for SSH from anywhere; UFW, unattended security upgrades and automatic reboots
  • A written runbook so each new project follows the same folder, naming, secrets and backup conventions

Stack

Ubuntu Server, Docker, Docker Compose, Cloudflare Tunnel, Cloudflare Access, Tailscale, Samba, Bash, cron, SSH
